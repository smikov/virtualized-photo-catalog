# ADR 020: Разбиение бандла и ленивые загрузки

**Статус:** принято (на основании замера)

## Проблема

Стандартная рекомендация — дробить бандл и подгружать код лениво. Нужно понять, даёт ли это что-то
конкретному приложению, а не применять практику по умолчанию.

Условия: одна страница, один сценарий загрузки, все зависимости нужны на первом экране.

## Варианты

### A. Один чанк (как есть)

**Плюсы:** один запрос; нет водопада загрузок; предсказуемое время до интерактивности.

**Минусы:** при выпуске новой версии браузер скачивает всё приложение целиком, даже если изменился один
компонент; для медленных сетей нет возможности показать часть интерфейса раньше.

### B. `manualChunks`: разделить вендоров по библиотекам

**Плюсы:** вендорные чанки не меняются между релизами — повторные визиты быстрее; параллельная загрузка
нескольких файлов.

**Минусы:** несколько запросов вместо одного; на HTTP/1.1 это заметнее; выигрыш появляется только при
повторных визитах и наличии кэша.

### C. `React.lazy` для тяжёлых частей (таблица)

**Плюсы:** библиотеки таблицы и виртуализации скачиваются после данных.

**Минусы:** создаёт водопад: сначала ответ API, потом запрос за чанком, потом рендер — то есть медленнее,
чем загрузить чанк параллельно с данными; при задержке сети эффект заметен.

### D. `React.lazy` по маршрутам

**Плюсы:** реальное сокращение первого чанка, когда страниц несколько.

**Минусы:** у приложения одна страница — делить нечего.

## Решение

Оставляем **один чанк**, сознательно отказавшись от разбиения и ленивых загрузок.

Аргументы подкреплены замером состава бандла (после сжатия):

| Часть                 | Размер  |
| --------------------- | ------- |
| React и React DOM     | ~68 КБ  |
| Табличная библиотека  | ~22 КБ  |
| HTTP-клиент           | ~21 КБ  |
| Валидация             | ~13 КБ  |
| Управление состоянием | ~9 КБ   |
| Код приложения        | ~5 КБ   |
| **Итого**             | ~140 КБ |

Из этого видно, что **основной вес — зависимости, а не наш код**: дробить приложение бессмысленно, объём
не изменится, изменится лишь число запросов.

## Почему

- **Одна страница — нечего делить.** Любой `import()` разложит те же модули по файлам, не уменьшив объём.
- **Всё нужное нужно сразу.** Экран состоит из панели загрузки, поиска и таблицы; ленивая загрузка таблицы
  добавила бы последовательный запрос там, где сейчас всё скачивается параллельно.
- **Единственный кандидат на ленивую загрузку (табличная библиотека) нужен на первом экране** — экономия
  22 КБ обменивается на задержку рендера.
- **Дробление вендоров — оптимизация кэша, а не первого экрана.** Она оправдана при реальном деплое с
  долгим кэшированием; сейчас её выигрыш не проявляется, а стоимость (несколько запросов) существует
  всегда.

## Последствия

**Получаем:**

- минимум запросов и предсказуемую загрузку без водопадов;
- простую сборку: один файл, который легко проверить и объяснить.

**Платим:**

- при выпуске новой версии пользователь скачивает весь бандл;
- нет возможности показать часть интерфейса до загрузки остального;
- при росте приложения (появление маршрутов, тяжёлых редких экранов) решение придётся пересматривать —
  и вот тогда эффект будет настоящим.

## Когда пересмотреть

- **Появление маршрутизации** — первый реальный повод: ленивые страницы дают сокращение первого чанка.
- **Появление тяжёлых редких сценариев** (редактор, графики, карты) — их выносить в отдельные чанки.
- **Реальный деплой с долгим кэшированием** — тогда разделение вендоров начинает окупаться.
