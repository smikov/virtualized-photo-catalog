# ADR 012: Поиск — debounce, фильтрация и подсветка

**Статус:** принято

## Проблема

Требование: поиск по таблице без кнопки «Найти» — результаты должны появляться после того, как
пользователь закончил вводить. Найденные совпадения нужно выделять цветом прямо в строках.

Осложняющие обстоятельства:

1. Фильтрация выполняется по 5000 записям на клиенте — нельзя запускать её на каждое нажатие клавиши.
2. Запрос приходит от пользователя, то есть может содержать символы, значимые для регулярных выражений.
3. После повторной загрузки данных старый запрос теряет смысл.

## Варианты

### A. Фильтрация на каждое нажатие клавиши

**Плюсы:** мгновенная реакция; никакого таймера.

**Минусы:** на быстром вводе — десятки фильтраций массива и перерисовок; при росте набора данных
интерфейс начнёт «заикаться»; лишняя нагрузка на главный поток.

### B. Debounce + клиентская фильтрация

**Плюсы:** один проход по данным после паузы; не нужна кнопка; предсказуемая нагрузка; при 5000 записях
фильтрация занимает доли миллисекунды.

**Минусы:** между вводом и результатом есть задержка (~300 мс); значение нужно хранить в двух местах (в
инпуте и в состоянии страницы).

### C. Кнопка «Найти»

**Плюсы:** полностью контролируемый момент запроса; проще всего.

**Минусы:** прямо противоречит требованию.

### D. Серверный поиск

**Плюсы:** масштабируется на любой объём; не требует загрузки всех данных.

**Минусы:** API не поддерживает поиск по подстроке; пришлось бы фильтровать на клиенте всё равно —
данные уже загружены целиком ради таблицы.

## Решение

1. **Debounce 300 мс** в компоненте поиска: значение хранится локально, наружу уходит усечённая строка
   после паузы ввода.
2. **Фильтрация — средствами таблицы** (см. ADR 010): запрос попадает в `globalFilter`, функция сравнения
   делает регистронезависимый поиск подстроки в заголовке.
3. **Подсветка — отдельный компонент**, который принимает текст и запрос, экранирует спецсимволы и
   оборачивает совпадения в `<mark>`. Стили — из токенов темы, а не «жёлтым маркером».
4. **Запрос сбрасывается при получении нового набора данных:** старый фильтр к новым данным не относится.

## Почему

- **Debounce — компромисс между отзывчивостью и нагрузкой.** 300 мс не ощущаются как задержка, но
  сокращают число фильтраций на порядок.
- **Фильтр живёт в модели таблицы, а не рядом.** Счётчик найденного, пустое состояние и будущая сортировка
  работают по одному и тому же набору строк — расхождений не возникает.
- **Экранирование обязательно.** Запрос — это пользовательский ввод, а подсветка строится через регулярное
  выражение; без экранирования ввод вроде `(special)` ломал бы разбор.
- **Подсветка вынесена из таблицы**, чтобы её можно было использовать отдельно (например, в карточках или
  подсказках) и тестировать без таблицы.

## Последствия

**Получаем:**

- поиск без кнопки с предсказуемой нагрузкой;
- подсветку всех совпадений в строке, безопасную к спецсимволам;
- единый источник истины для числа найденных записей.

**Платим:**

- клиентская фильтрация ограничена загруженным набором данных;
- введённое значение дублируется: локально в инпуте и в состоянии страницы;
- для серверного поиска потребуется перевести таблицу в ручной режим фильтрации и отказаться от подсветки
  силами клиента.

## Когда пересмотреть

- Если набор данных перестанет помещаться в память — поиск уходит на сервер, а подсветка становится
  задачей бэкенда.
- Если появятся дополнительные условия поиска (по альбому, по диапазону идентификаторов) — вместо
  глобального фильтра понадобится набор колонковых фильтров с интерфейсом.
