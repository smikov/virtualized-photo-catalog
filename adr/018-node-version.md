# ADR 018: Версия Node и воспроизводимость окружения

**Статус:** принято

## Проблема

Версия рантайма влияет на всё: сборку, тесты, поведение зависимостей. Если она зафиксирована в разных
местах по-разному (или не зафиксирована вовсе), появляется классическая ситуация «у меня работает»: код
проверен на одной версии, в CI — другая, в контейнере — третья.

Отдельная тонкость: инструменты разработки объявляют поддерживаемые диапазоны версий. Тестовый раннер,
например, может не поддерживать старую LTS — тогда зелёный результат зависит от везения, а не от
совместимости.

## Варианты

### A. Не фиксировать версию

**Плюсы:** ничего не нужно поддерживать; работает «на любой» версии.

**Минусы:** результаты невоспроизводимы; инструменты молча попадают в неподдерживаемые диапазоны; ошибки
окружения выглядят как ошибки кода.

### B. Указать диапазон в манифесте, остальное — на усмотрение

**Плюсы:** минимальная формальность; не мешает разработке.

**Минусы:** диапазон не гарантирует совместимости с инструментами; Docker и CI могут расходиться между
собой; никто не проверяет фактическую версию.

### C. Точная фиксация во всех местах: `.nvmrc`, `engines`, образ, CI, типы

**Плюсы:** одна версия везде; окружение воспроизводимо; типы рантайма соответствуют фактическому рантайму.

**Минусы:** версию нужно поднимать в нескольких местах одновременно; разработчику требуется переключить
локальную версию.

### D. Жёсткое принуждение (`engine-strict`)

**Плюсы:** несовпадение версии немедленно ломает установку — расхождение невозможно не заметить.

**Минусы:** новичок получает непонятную ошибку установки вместо подсказки; в некоторых окружениях
(например, CI с другим образом) это блокирует работу без явной на то причины.

## Решение

Фиксируем **одну точную версию** во всех местах сразу:

| Место                    | Что фиксирует                               |
| ------------------------ | ------------------------------------------- |
| `.nvmrc`                 | Версия для локальной разработки             |
| `engines` в манифесте    | Требование к окружению (диапазон по мажору) |
| `Dockerfile`             | Версия в образе                             |
| Конфигурация CI          | Версия на раннере                           |
| Типы рантайма (`@types`) | API, доступные в этой версии                |

Дополнительно: типы рантайма обязаны соответствовать фактической версии — иначе они разрешают API,
которых в рантайме нет.

Принуждение через `engine-strict` сознательно не включено: предупреждение при установке достаточно, а
жёсткий отказ мешает в окружениях, где версия управляется извне.

## Почему

- **Расхождение между местами — и есть источник проблемы.** Фиксация в одном файле бессмысленна, если
  образ собирается на другой версии.
- **Точная версия, а не «последняя из мажора».** Минорные обновления приносят изменения поведения
  (например, флаги и загрузчики модулей), и «одна и та же» версия на разных машинах ведёт себя по-разному.
- **Совместимость с инструментами проверяется фактом, а не обещанием.** Выбранная версия входит в
  поддерживаемые диапазоны всех ключевых инструментов — это проверено прогоном, а не предположено.
- **Типы, соответствующие рантайму, убирают целый класс ошибок:** код, который типизируется, но падает при
  запуске.

## Последствия

**Получаем:**

- одинаковое поведение локально, в CI и в контейнере;
- отсутствие «необъяснимых» падений сборки и тестов;
- явное требование к окружению, которое видно новому участнику.

**Платим:**

- поднимать версию нужно сразу в нескольких местах — рассинхронизация возвращает проблему;
- на другой локальной версии появляется предупреждение при установке зависимостей;
- обслуживание: раз в полгода-год версию нужно пересматривать вместе с зависимостями.

## Когда пересмотреть

- При переходе на новую LTS — обновить все места одновременно и зафиксировать причину.
- Если проект начнут собирать на нескольких версиях рантайма, понадобится матрица в CI и более широкий
  диапазон в `engines`.
