# ADR 003: Импорты — алиасы путей и публичное API слоёв

**Статус:** принято

## Проблема

При слоистой структуре пути становятся глубокими: `../../../../features/search-photos/ui/HighlightText`.
Это создаёт три проблемы:

1. **Хрупкость.** Перенос файла внутри слайса ломает импорты у всех потребителей.
2. **Протечки.** Импорт вглубь (`features/x/ui/HighlightText`) связывает внешний код с внутренним
   устройством слайса: переименование папки становится ломающим изменением.
3. **Читаемость.** По строке импорта невозможно понять, к какому слою и слайсу относится модуль.

## Варианты

### A. Только относительные пути

**Плюсы:** ничего не настраивать; работает в любом инструменте без конфигурации.

**Минусы:** количество `../` растёт с глубиной; при переносе файла приходится править импорты; случайный
импорт вверх по слоям выглядит так же, как обычный.

### B. Только алиасы (`@/features/...`)

**Плюсы:** путь не зависит от расположения файла; видно слой и слайс; импорты читаются одинаково.

**Минусы:** внешнему коду по-прежнему доступно внутреннее устройство слайса — алиас просто сокращает путь
к нему.

### C. Алиасы + barrel-файл (`index.ts`) в каждом слайсе

**Плюсы:** снаружи виден только публичный контракт слайса; внутренние файлы можно переставлять свободно;
по составу barrel-файла понятно, что слайс предоставляет.

**Минусы:** barrel нужно поддерживать; при неаккуратном экспорте он может утянуть в бандл лишние модули;
циклические зависимости между barrel-файлами сложнее заметить.

### D. Автоматическая генерация публичного API

**Плюсы:** barrel-файлы не расходятся с кодом.

**Минусы:** ещё один инструмент и шаг сборки; для проекта такого размера — избыточно.

## Решение

1. **Алиас `@/` → `src/`**, объявленный согласованно в трёх местах: описание типов, конфигурация сборки,
   конфигурация тестов. Расхождение между ними — самая частая поломка, поэтому синхронность проверяется
   тем, что все три файла лежат в репозитории рядом.
2. **Barrel-файл в каждом слайсе**: `features/load-photos/index.ts`, `entities/photo/index.ts` и так далее.
   Наружу — только то, что действительно нужно: компоненты, thunk'и, селекторы, типы.
3. **Внутренние детали не экспортируются**: экшены, которые вызывает только собственный thunk, и
   вспомогательные функции остаются внутри слайса.

## Почему

- **Публичное API как контракт.** Внешний код не должен знать, что `HighlightText` лежит в `ui/` — он
  импортирует `@/features/search-photos`. Перестановка файлов внутри слайса перестаёт быть ломающим
  изменением.
- **Алиас решает только длину пути, barrel — связность.** Мы берём оба инструмента, потому что они решают
  разные задачи: читаемость импорта против инкапсуляции.
- **Три barrel-файла вместо одного общего.** Общий `shared/index.ts` на всё привёл бы к тому, что любой
  импорт из `shared` тянул бы весь слой. Barrel на слайс ограничивает область.
- **Трейд-офф с tree-shaking принят сознательно:** в barrel попадают только лёгкие модули (компоненты и
  модель), тяжёлые зависимости не реэкспортируются.

## Последствия

**Получаем:**

- импорты, не зависящие от глубины вложения файла;
- явную границу «что слайс предоставляет наружу»;
- возможность свободно переставлять файлы внутри слайса.

**Платим:**

- barrel нужно обновлять при добавлении экспорта — иначе публичное API отстаёт от кода;
- алиас живёт в трёх конфигурациях, и их нужно держать согласованными;
- циклические зависимости между barrel-файлами автоматически не обнаруживаются — это зона внимания при
  ревью.

## Когда пересмотреть

- При появлении монорепозитория публичное API переезжает на уровень пакетов (`exports` в `package.json`).
- Если проект вырастет до десятков слайсов, стоит добавить правило, запрещающее импорт «вглубь» чужого
  слайса автоматически — сейчас это соглашение, а не проверка.
