# ADR 007: Как считать прогресс загрузки

**Статус:** принято

## Проблема

Требование — показывать прогресс загрузки в процентах. Естественная единица измерения — байты: процент
равен `загружено / всего`. Но у используемого API это невозможно по двум причинам сразу:

1. Ответ отдаётся потоком без заголовка `Content-Length` (chunked + сжатие), то есть общего размера
   просто нет.
2. Даже если бы сервер его отдавал, заголовок `Content-Length` не входит в список заголовков,
   доступных браузеру при кросс-доменном запросе, — приложение на другом origin его не увидит.

Дополнительное требование: проценты должны быть честными. Симуляция таймером (0 → 80 → 95%) выглядит
правдоподобно, но не отражает реальность: пользователь видит «80%» ещё до получения данных.

## Варианты

### A. Проценты по байтам

**Плюсы:** идеальная точность и гранулярность; не зависит от структуры данных.

**Минусы:** нереализуемо для этого API: размера ответа нет и он недоступен из браузера.

### B. Симуляция прогресса таймером

**Плюсы:** выглядит плавно; не зависит от сервера.

**Минусы:** вводит в заблуждение: проценты не связаны с сетью; при медленном соединении прогресс
«залипает» на 95%, при быстром — данные приходят раньше, чем полоса дошла до половины.

### C. Неопределённый индикатор

**Плюсы:** честно; работает для любого API; не требует изменений в загрузке.

**Минусы:** не выполняет требование «прогресс в процентах».

### D. Проценты по числу полученных страниц

**Плюсы:** честно (каждая страница — реально полученные данные); API поддерживает постраничную выдачу и
сообщает общее число записей заголовком `X-Total-Count`, доступным браузеру; масштабируется на любой
объём данных; отмена и повтор работают постранично.

**Минусы:** число запросов растёт (10 страниц вместо одного запроса); гранулярность процента равна
размеру страницы; появляется зависимость от конкретного заголовка.

## Решение

Загрузка идёт страницами, прогресс считается по числу полученных страниц.

1. **Размер страницы задаётся конфигурацией** и определяет гранулярность: 500 записей при общем объёме
   5000 дают шаг 10%.
2. **Общее число записей берётся из `X-Total-Count`.** Если заголовка нет — используется явно заданное
   значение из конфигурации, а если и его нет — загрузка идёт последовательно до первой неполной страницы,
   и тогда процент не показывается.
3. **Процент ограничен 99% до финального склеивания:** полоса не должна доходить до конца раньше данных.
4. **Страницы собираются по номеру, а не по порядку прихода.** Порядок записей в таблице не должен
   зависеть от скорости ответов.
5. **При неизвестном общем числе показывается бегущая полоса и количество уже загруженных записей** —
   честный индикатор вместо выдуманных процентов.

## Почему

- **Честность важнее плавности.** Пользователь, видящий 40%, должен получать ровно 40% данных. Любая
  симуляция ломает это свойство и маскирует реальные проблемы сети.
- **Страница — естественная единица для этого API.** Единственная метрика, которую сервер сообщает явно, —
  общее число записей; страницы дают точку отсчёта без догадок.
- **Режим без `X-Total-Count` предусмотрен.** Приложение не ломается на API, которое не отдаёт заголовок,
  а деградирует до честного неопределённого индикатора.
- **Гранулярность — параметр, а не свойство кода.** Если нужен шаг 2%, достаточно уменьшить размер
  страницы; логика не меняется.

## Последствия

**Получаем:**

- честные проценты, привязанные к реально полученным данным;
- настраиваемую гранулярность и объём;
- естественную основу для роста: для большого объёма данных та же механика превращается в загрузку по
  требованию.

**Платим:**

- несколько запросов вместо одного: 5000 записей — это 10 запросов при размере страницы 500;
- шаг прогресса равен размеру страницы: бар движется ступенями;
- постраничная загрузка требует согласования с параллельностью (см. ADR 011 о виртуализации и ADR 009 о
  повторах).

## Когда пересмотреть

- Если появится API с `Content-Length` (собственный бэкенд), точный процент по байтам станет возможен.
- Для миллионов записей предзагрузка всего набора перестанет быть разумной: тогда нужна загрузка по
  требованию — только тех страниц, которые видны, с прогрессом по видимой области.
