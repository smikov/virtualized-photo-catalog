# ADR 008: Отмена запросов

**Статус:** принято

## Проблема

Пользователь должен уметь прервать загрузку кнопкой. Прерывание означает не «перестать обновлять
интерфейс», а реально закрыть HTTP-запросы: иначе трафик тратится впустую, а сервер продолжает работу.

Инструмент для этого один — `AbortController`. Сложность в том, что:

- контроллер нельзя хранить в Redux: он не сериализуется, ломает DevTools и заставляет редьюсеры делать
  побочные эффекты;
- редьюсеры обязаны быть чистыми функциями;
- контроллер нужен асинхронной логике (thunk), которая живёт вне дерева компонентов;
- одновременно может быть несколько активных запросов (постраничная загрузка).

## Варианты

### A. Модульная переменная в файле слайса

**Плюсы:** минимальный код; контроллер доступен отовсюду, где импортирован модуль.

**Минусы:** состояние общее для всего процесса — два экземпляра приложения (тесты, серверная отрисовка)
мешают друг другу; тесты вынуждены вызывать сброс и знать про внутреннее устройство; подменить поведение
можно только правкой модуля.

### B. Контроллер в Redux-состоянии

**Плюсы:** «всё состояние в одном месте».

**Минусы:** невозможно: объект не сериализуется, DevTools ломаются, редьюсер перестаёт быть чистой
функцией.

### C. Реестр как зависимость, передаваемая в thunk (`thunk.withExtraArgument`)

**Плюсы:** экземпляр создаётся при инициализации приложения и принадлежит ему; тесты создают свой реестр и
полностью изолированы; реализацию можно подменить (другая политика отмены) без правки кода фичи; состояние
не покидает замыкание.

**Минусы:** появляется дополнительный параметр в конфигурации thunk'ов; в тестах нужно один раз собрать
store с этим параметром.

### D. Отмена через собственный middleware

**Плюсы:** централизованно; можно отменять по типу действия.

**Минусы:** свой протокол вместо штатного механизма RTK; больше кода и собственных ошибок; всё равно нужен
реестр контроллеров внутри.

## Решение

1. **Фабрика реестра** (`createRequestRegistry`) с тремя операциями: `start()` — прерывает предыдущий
   запрос и возвращает новый контроллер, `finish(controller)` — освобождает ссылку, если она всё ещё
   указывает на завершившийся запрос, `abortCurrent()` — прерывает текущий.
2. **Экземпляр создаётся в слое `app`** при сборке стора и передаётся в thunk'и через
   `thunk.withExtraArgument`.
3. **Один контроллер на всю загрузку.** Все страницы используют его сигнал, поэтому одно нажатие «Отменить»
   прерывает и текущую страницу, и остальные запросы пула.
4. **Отмена не считается ошибкой:** состояние переходит в `cancelled`, пользователь видит нейтральное
   сообщение и кнопку повтора.

## Почему

- **Изоляция состояния — главное.** Реестр в замыкании экземпляра означает, что параллельные экземпляры
  приложения не влияют друг на друга, а тесты не нуждаются в глобальном сбросе.
- **DI вместо глобальной переменной** даёт возможность заменить политику отмены (например, «отменять
  только последнюю страницу») без изменения кода фичи.
- **Штатный механизм RTK предпочтительнее своего middleware:** меньше кода, который нужно поддерживать, и
  предсказуемое поведение для тех, кто знаком с библиотекой.
- **Один контроллер на пачку запросов достаточно.** Постраничная загрузка — это одна операция с точки
  зрения пользователя, поэтому и отмена у неё одна.

## Последствия

**Получаем:**

- реальное прерывание запросов, а не только остановку интерфейса;
- изолированное состояние: тесты не делят контроллеры между собой;
- возможность подменить реализацию реестра без правок фичи.

**Платим:**

- тип конфигурации thunk'ов расширяется — при добавлении новых зависимостей его нужно править в одном
  месте;
- в тестах стор нужно собирать с этим параметром (три строки);
- реестр держит один активный контроллер: параллельные независимые загрузки (например, две разные фичи)
  потребуют либо разных реестров, либо расширения интерфейса до набора.

## Когда пересмотреть

- Если появятся независимые параллельные загрузки — интерфейс реестра расширяется до набора контроллеров
  с ключами.
- Если понадобится «мягкая» отмена (дождаться текущей страницы и не начинать следующую) — это другая
  политика, и её стоит реализовывать как вторую реализацию интерфейса, а не как ветвление в существующей.
