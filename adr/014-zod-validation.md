# ADR 014: Валидация данных на границе — Zod

**Статус:** принято

## Проблема

TypeScript проверяет типы во время компиляции: `axios.get<Photo[]>()` — это наше обещание, что сервер
вернёт именно такой массив, а не гарантия. Если внешний API изменит формат (например, `id` придёт
строкой или пропадёт `thumbnailUrl`), приложение упадёт при отрисовке — в случайном месте и с непонятной
ошибкой.

Вторая граница того же рода — переменные окружения: неверный адрес API или нецелое число попыток
обнаруживаются только тогда, когда что-то уже не работает.

## Варианты

### A. Только типы TypeScript

**Плюсы:** ничего не подключать; ноль накладных расходов.

**Минусы:** никакой защиты от рантайма; ошибка контракта превращается в падение интерфейса; диагностика
затруднена — непонятно, что именно пришло не так.

### B. Ручные проверки

**Плюсы:** без зависимостей; полный контроль.

**Минусы:** на вложенных структурах превращается в нечитаемую простыню; каждая новая проверка — новый код
и новые тесты; легко забыть поле при изменении модели.

### C. Zod

**Плюсы:** схема описывается декларативно; тип выводится из схемы — нельзя изменить одно и забыть другое;
подробные сообщения с путём до проблемного поля; одна и та же библиотека валидирует и ответ API, и
переменные окружения.

**Минусы:** +13 кБ в бандле; валидация 5000 записей стоит времени (десятки миллисекунд); схему нужно
поддерживать в актуальном состоянии.

### D. io-ts или valibot

**Плюсы:** сопоставимые возможности; valibot заметно легче.

**Минусы:** у io-ts более громоздкий API и хуже сообщения об ошибках; valibot — менее распространён и
хуже знаком команде. Для проекта такого размера разница в весе не критична.

## Решение

1. **Схема сущности и списка** описана один раз; тип сущности **выводится** из схемы (`z.infer`), а не
   дублируется рядом.
2. **Валидация выполняется на границе** — сразу после получения ответа, постранично. Невалидный ответ не
   попадает в состояние: загрузка завершается ошибкой с перечнем первых проблем.
3. **Та же библиотека валидирует переменные окружения при старте.** Конфигурация с невалидным адресом
   падает сразу и с понятным списком, а не при первом обращении к API.

## Почему

- **Один источник истины для типа и проверки.** Дублирование «интерфейс + ручной валидатор» неизбежно
  расходится; вывод типа из схемы делает расхождение невозможным.
- **Постраничная валидация локализует проблему.** При ошибке в одной странице понятно, где именно нарушен
  контракт, и остальные данные не смешиваются с мусором.
- **Ранний отказ на старте дешевле.** Ошибка конфигурации, обнаруженная при запуске, — это сообщение в
  консоли; обнаруженная при загрузке — это пустой экран и вопрос «почему».
- **Цена в 13 кБ приемлема:** взамен получаем диагностируемость контракта и отсутствие падений в рендере.

## Последствия

**Получаем:**

- невалидный ответ сервера не ломает интерфейс, а даёт понятную ошибку;
- тип сущности не может разойтись со схемой;
- конфигурация проверяется до запуска приложения.

**Платим:**

- +13 кБ в бандле;
- валидация 5000 записей добавляет десятки миллисекунд к загрузке;
- схему нужно обновлять при изменении контракта — это дисциплина, а не автоматика.

## Когда пересмотреть

- Если бандл станет критичным, стоит рассмотреть более лёгкую библиотеку или валидацию только на сервере.
- Если появится OpenAPI-схема бэкенда, генерация валидаторов и типов из неё снимет ручную поддержку.
