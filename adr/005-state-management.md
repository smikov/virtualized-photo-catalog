# ADR 005: Управление состоянием — Redux Toolkit

**Статус:** принято

## Проблема

Состояние загрузки нужно в двух местах одновременно: панель управления загрузкой (статус, прогресс,
кнопки) и страница (решениe, показывать ли поиск и таблицу). Кроме данных и статуса есть производные
величины — количество загруженных записей, процент, номер текущего запроса.

Дополнительно нужна асинхронная логика, которую нельзя привязать к жизненному циклу одного компонента:
загрузка продолжается, пока пользователь взаимодействует с интерфейсом, и должна переживать
перерисовки.

## Варианты

### A. Локальное состояние + передача через пропсы

**Плюсы:** ничего не подключать; всё в одном компоненте; проще всего для одного экрана.

**Минусы:** данные нужны в двух поддеревьях, значит появляется цепочка пропсов; асинхронная логика
оказывается внутри компонента, её сложно тестировать отдельно от разметки; отмена и повторные попытки
привязываются к жизненному циклу компонента.

### B. Context API

**Плюсы:** встроено в React; не нужны зависимости; достаточно для одного-двух значений.

**Минусы:** при частых обновлениях (прогресс меняется несколько раз в секунду) перерисовываются все
подписчики контекста; нет инструментов для асинхронных переходов и отмены; DevTools ограничены.

### C. Redux Toolkit + createAsyncThunk

**Плюсы:** единый стор; предсказуемые переходы `pending` / `fulfilled` / `rejected`; `requestId` в
метаданных позволяет отбрасывать результаты устаревших запросов; DevTools показывают всю историю действий;
middleware позволяет передать зависимости (реестр запросов) в асинхронную логику.

**Минусы:** больше кода, чем у локального состояния; появляется собственный слой действий и редьюсеров;
для серверного кеша возможностей не хватает — инвалидацию и фоновое обновление придётся писать руками.

### D. Zustand или Jotai

**Плюсы:** минимальный шаблон; нет редьюсеров; подписки точечные.

**Минусы:** меньше структуры для асинхронных сценариев (статусы, отмена, гонки приходится описывать
самим); команде привычнее Redux DevTools и привычная модель потока данных.

### E. TanStack Query

**Плюсы:** лучший инструмент именно для серверного состояния: кеш, повторные запросы, инвалидация,
состояния загрузки — из коробки.

**Минусы:** задача требует ручного контроля прогресса и отмены на уровне отдельного запроса; логика
постраничной загрузки с общим процентом плохо ложится на модель «один запрос — одно состояние»;
пришлось бы обходить библиотеку вместо того, чтобы её использовать.

## Решение

Redux Toolkit: один срез `loadPhotos` с состоянием загрузки, thunk для загрузки, thunk для отмены и
селекторы как публичный контракт.

Ключевые детали:

1. **`currentRequestId` в состоянии.** Каждый запрос помечается идентификатором; результат запроса с
   чужим идентификатором игнорируется. Без этого ответ устаревшего запроса мог перезаписать актуальные
   данные.
2. **Редьюсеры остаются чистыми.** «Побочные» ресурсы (контроллеры отмены) в состояние не попадают — они
   передаются в thunk как зависимость (см. ADR 008).
3. **Селекторы — часть публичного API.** Компоненты не читают срез напрямую: форма состояния может
   меняться, пока контракт остаётся.

## Почему

- **Состояние читается из двух мест независимо.** Панель и страница подписываются на нужные поля
  точечно, без знания друг о друге.
- **Асинхронные переходы описаны явно.** `pending` / `fulfilled` / `rejected` — это готовый автомат
  состояний, а не набор булевых флагов, которые легко привести в противоречивое состояние.
- **`requestId` — единственный способ надёжно победить гонки.** Пользователь может нажать «Повторить»,
  пока жив старый запрос; без сравнения идентификаторов результат непредсказуем.
- **TanStack Query отклонён осознанно:** его сильные стороны (кеш, инвалидация) нам не нужны, а то, что
  нужно (процент по страницам, отмена, повторы) — пришлось бы делать вопреки его модели.

## Последствия

**Получаем:**

- предсказуемый поток данных с историей действий в DevTools;
- защиту от гонок через `requestId`;
- возможность тестировать логику загрузки отдельно от компонентов.

**Платим:**

- шаблонный код: срез, thunk'и, типы;
- нет кеша серверных данных и фонового обновления — при появлении таких требований часть логики придётся
  переписать или добавить TanStack Query рядом для других экранов;
- в состоянии лежат все 5000 записей; при росте объёма данных понадобится загрузка по требованию.

## Когда пересмотреть

- Если появится второй экран с серверными данными и потребуется кеш с инвалидацией — стоит рассмотреть
  TanStack Query для этих экранов.
- Если объём данных вырастет на порядок, хранение всего набора в сторе станет узким местом (см. ADR 007).
