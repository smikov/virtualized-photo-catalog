# ADR 009: Обработка ошибок и повторные попытки

**Статус:** принято

## Проблема

Внешний API может отвечать по-разному: сеть недоступна, соединение «висит», сервер вернул 500, сервер
вернул 404, ответ пришёл в неожиданном формате. Каждая ситуация требует своего поведения:

- сетевой сбой и 5xx — временные, повтор имеет смысл;
- 404 или 400 — постоянные, повтор гарантированно провалится, но займёт время пользователя;
- «зависшее» соединение без таймаута не завершится никогда — повтор не начнётся;
- отмена пользователем — вообще не ошибка;
- ответ неверного формата — ошибка контракта, её нельзя «переповторить».

## Варианты

### A. Повторять любую ошибку

**Плюсы:** просто; одна ветка кода.

**Минусы:** на 404 пользователь ждёт три попытки с паузами, чтобы увидеть ту же ошибку; бессмысленная
нагрузка на сервер; задержка реакции на постоянные ошибки.

### B. Не повторять вообще

**Плюсы:** предсказуемо; быстрый отказ.

**Минусы:** любая кратковременная проблема сети превращается в ошибку на экране — при постраничной
загрузке вероятность сбоя хотя бы одной страницы заметно выше.

### C. Повторять только временные сбои, с таймаутом

**Плюсы:** пользователь не видит мигающих сетевых ошибок; постоянные ошибки всплывают сразу; «зависшее»
соединение прерывается таймаутом.

**Минусы:** нужно классифицировать ошибки по статусу и наличию ответа; политика требует тестов.

### D. Экспоненциальный backoff с джиттером

**Плюсы:** лучше для перегруженного сервера; снижает эффект «стада».

**Минусы:** для одного-двух параллельных запросов избыточен; усложняет тесты и время ожидания
пользователя.

## Решение

1. **Таймаут на каждый запрос** (по умолчанию 15 секунд) — конфигурируемый.
2. **Повторяем только временные сбои:** отсутствие ответа (сеть, обрыв, таймаут), статусы 408, 429 и 5xx.
3. **Не повторяем ошибки клиента** (400, 403, 404 и прочие 4xx): сразу сообщение вида «Сервер ответил
   ошибкой 404».
4. **Отмена не является ошибкой:** распознаётся отдельно и не запускает повтор.
5. **Число попыток и пауза — параметры конфигурации**; пауза прерывается отменой, слушатель снимается,
   чтобы не накапливать утечки между попытками.
6. **Ошибки переводятся в собственные сообщения** с сохранением исходной причины (`cause`) — прикладной
   код не видит формат библиотеки.

## Почему

- **Повтор — это обещание, что станет лучше.** Если повтор не может изменить результат (404), он только
  тратит время. Классификация по статусу — минимально достаточный критерий.
- **Таймаут обязателен именно потому, что мы повторяем.** Без него «зависшее» соединение занимает попытку
  навсегда, и весь механизм повторов бесполезен.
- **Backoff отклонён для текущего масштаба:** три попытки на страницу с фиксированной паузой — предсказуемо
  и достаточно. При росте числа одновременных запросов решение стоит пересмотреть.
- **Сохранение причины** важно для отладки: сообщение для пользователя короткое, а исходная ошибка
  доступна в отчёте.

## Последствия

**Получаем:**

- кратковременные сбои не видны пользователю;
- постоянные ошибки видны сразу и с понятным текстом;
- «зависшие» соединения не блокируют загрузку навсегда;
- единая политика для всех запросов приложения.

**Платим:**

- фиксированная пауза не адаптируется к нагрузке; при массовых параллельных запросах понадобится backoff;
- классификация опирается на коды статусов — нестандартный сервер может потребовать дополнительных правил;
- настройки (попытки, пауза, таймаут) добавляют поверхность конфигурации.

## Когда пересмотреть

- При росте числа одновременных запросов — перейти на backoff с джиттером.
- Если появится idempotency-ключ или серверная поддержка повторных запросов, политику можно сделать
  агрессивнее.
- Если появится офлайн-режим, повторные попытки станут частью очереди, а не локального цикла.
