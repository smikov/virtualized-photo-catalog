# ADR 002: Слои приложения — Feature-Sliced Design

**Статус:** принято

## Проблема

Приложение состоит из одной страницы, но внутри неё уже живут загрузка данных, поиск, виртуализированная
таблица, валидация и глобальное состояние. Без правил структура деградирует предсказуемо: компонент
начинает импортировать соседа напрямую, «временный» хелпер оседает в общей папке, а изменение формата
данных затрагивает половину проекта.

Нужна методология, которая:

1. отвечает на вопрос «куда положить новый код» без обсуждений;
2. запрещает импорты «снизу вверх» — чтобы нижние модули не зависели от верхних;
3. проверяется автоматически, а не держится на памяти команды;
4. позволяет добавлять фичи, не редактируя чужие модули.

## Варианты

### A. Плоская структура (`components/`, `hooks/`, `utils/`)

**Плюсы:** минимальный порог входа; ничего не нужно объяснять; быстро на старте.

**Минусы:** через несколько недель `components` превращается в свалку; неясно, где бизнес-логика, а где
переиспользуемый UI; любые два модуля могут импортировать друг друга, циклические зависимости появляются
незаметно.

### B. Модули по доменам (стиль Nx / `features/*` без слоёв)

**Плюсы:** код группируется по смыслу; проще, чем полноценная методология; хорошо ложится на монорепозиторий.

**Минусы:** не отвечает на вопрос про переиспользуемый код (HTTP-клиент, конфиг, провайдеры); границы
модулей приходится придумывать заново в каждом проекте; нет общепринятого правила импортов.

### C. Feature-Sliced Design

**Плюсы:** фиксированные слои (`app`, `pages`, `widgets`, `features`, `entities`, `shared`) и одно
направление зависимостей; правила формулируются как конфигурация линтера; слои можно вводить постепенно —
начать с трёх и добавлять по мере роста.

**Минусы:** больше сущностей, чем в плоской структуре; появляются barrel-файлы, которые нужно поддерживать;
новичку нужно один раз прочитать правила.

## Решение

Используем FSD с шестью слоями и строгим направлением импортов сверху вниз:

| Слой       | Ответственность                                          | Что лежит у нас                                           |
| ---------- | -------------------------------------------------------- | --------------------------------------------------------- |
| `app`      | Инициализация, провайдеры, глобальные стили, точка входа | `index.tsx`, `ui/App.tsx`, `store`, `providers`, `styles` |
| `pages`    | Композиция экрана из виджетов и фич                      | `photos-page`                                             |
| `widgets`  | Самостоятельные блоки интерфейса                         | `photos-table`                                            |
| `features` | Действия пользователя                                    | `load-photos`, `search-photos`                            |
| `entities` | Бизнес-сущности и доступ к их данным                     | `photo` (схема, загрузка страницы)                        |
| `shared`   | Инфраструктура без знания о домене                       | `api`, `config`, `lib`                                    |

Правила запретов записаны в конфигурации ESLint: каждый слой получает `no-restricted-imports` со списком
вышестоящих слоёв — и в виде алиаса (`@/pages/...`), и в виде относительного пути (`../../pages/...`).

## Почему

- **Одно направление зависимостей решает главную проблему.** HTTP-клиент и валидация не могут внезапно
  начать зависеть от страницы — это ошибка сборки, а не пожелание на ревью.
- **Правило проверяется машинной.** Мы сознательно не полагаемся на дисциплину: правило `no-restricted-imports`
  срабатывает на оба вида импорта, включая обход через относительные пути.
- **Слои совпадают с вопросами, которые возникают при разработке.** «Это действие пользователя или
  отображение сущности?» — на такой вопрос FSD отвечает однозначно, поэтому новые файлы не спорят о месте.
- **Методология допускает рост.** Сейчас `entities` содержит одну сущность, а `widgets` — один виджет.
  Появление второй сущности не потребует перестройки: место для неё уже определено.

## Последствия

**Получаем:**

- предсказуемое место для нового кода;
- запрет импортов вверх по слоям — проверяется линтером, включая относительные пути;
- возможность удалить фичу вместе с её папкой, не вычищая ссылки по всему проекту.

**Платим:**

- появляются barrel-файлы, которые нужно обновлять при добавлении экспортов;
- у проекта больше структуры, чем требует одна страница, — это осознанный задел на рост;
- одно исключение всё же есть: доступ к типизированным хукам стора (см. ADR 004).

## Когда пересмотреть

- Если приложение останется одностраничным демо навсегда, слои `widgets` и `pages` будут избыточны — тогда
  достаточно `features` и `shared`.
- Если появятся несколько приложений с общим кодом, понадобится монорепозиторий, и границы придётся
  формулировать между пакетами, а не только между папками.
